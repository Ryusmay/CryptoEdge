# CryptoEdge v20.17.0

## Bramka charakterystyki dla decyzji ryzyka

Etap czwarty miał przenieść risk do `cryptoedge/risk/`. Zanim to zrobiłem,
sprawdziłem, czym bym to udowodnił — i okazało się, że niczym.

Bramka parytetu (`tools/parity.py`) pokrywa replay, a replay woła
`DecisionPipeline` z `risk=None` i stosuje własne limity slotów. Znaczy to,
że około 700 linii `risk_manager.py` — `can_open_position()`,
`calculate_position_size()` i pomocnicy — nie było objęte żadną bramką.
Przeniesienie tej logiki byłoby dziś nieudowadnialne, a jest to kod
decydujący, czy wolno otworzyć pozycję i jak dużą.

Ten etap domyka lukę zamiast przenosić logikę na wyczucie.

```
python tools/risk_gate.py                   # porównaj z baseline
python tools/risk_gate.py --write-baseline  # zapisz nowy punkt odniesienia
python tools/risk_gate.py --coverage        # jakie powody pokrywa korpus
```

- 88 kontrolowanych przypadków przechodzi przez **prawdziwy** `RiskManager`;
  zapisywany jest werdykt: zgoda, powód i rozmiar pozycji.
- Stan konta jest ustawiany jawnie w całości — kapitał, liczba pozycji, halt,
  pauza, reżim, `risk_state`, dzienny PnL, kierunki otwartych pozycji — więc
  wynik nie zależy od kolejności testów ani od śmieci po poprzednim przebiegu.
- Wyjątek też jest wynikiem. Ukrycie go zamieniłoby bramkę w źródło fałszywego
  spokoju; obecnie żaden przypadek nie rzuca.
- Baseline zawiera ten sam odcisk konfiguracji co bramka parytetu, więc zmiana
  dowolnego progu jest widoczna jako zmiana konfiguracji, nie jako tajemnicza
  zmiana werdyktu.
- Bramka chodzi w `run_tests.py` (`tests/test_risk_gate_baseline.py`), a nie
  tylko na żądanie. Osobne testy pilnują, żeby korpus nie stracił pokrycia.

Korpus pokrywa 20 różnych powodów, w tym `INVALID_DIRECTION`, `INVALID_PRICE`,
`NON_POSITIVE_NET_R`, `DAILY_PROJECTED_LOSS`, `CLUSTER_RISK`,
`RISK_REDUCE_ONLY`, `HEAT_LONG`, `Max pozycji`, `Kapital zbyt niski` oraz progi
siły osobno dla `trend` i `reversal`.

## Czego korpus celowo nie obejmuje

Aktywnych cooldownów. Ich powód zawiera pozostałe minuty liczone z
`datetime.now()`, więc baseline dryfowałby między przebiegami. Cooldowny mają
własne testy jednostkowe; tutaj są wygaszone, a osobny test pilnuje, żeby nie
wróciły do baseline tylnymi drzwiami.

## Co przy okazji wyszło

Pierwsza wersja korpusu dawała podejrzanie dużo zgód: sygnał o sile 0.30 przy
progu `MIN_SIGNAL_STRENGTH = 0.48` przechodził. To nie jest błąd — bramka siły
jest **celowo pomijana** dla `DAYTRADING_V2`, bo V2 ma własne kontrole
w silniku i podaje stałą `strength = 0.75`. Korpus był naiwny, nie kod.
Zostało to udokumentowane osobnym przypadkiem
`strength_v2_low_is_skipped_by_design`, żeby ta decyzja projektowa była
widoczna, a nie wyglądała na dziurę.

## Weryfikacja

- Pełny zestaw: 937 testów, OK (przed zmianami 929).
- `python tools/risk_gate.py` → `IDENTYCZNIE`, dwa niezależne przebiegi zgodne.
- `python tools/parity.py` → `IDENTYCZNIE`.
- Żaden plik produkcyjny nie został w tym etapie zmieniony.

Przeniesienie `can_open_position()` i `calculate_position_size()` do
`cryptoedge/risk/` — teraz z bramką, która to udowodni.
