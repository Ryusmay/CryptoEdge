# v20.38.2 — bramki znow odtwarzalne na czystym klonie + wylaczony ukryty eksperyment

Dwie rzeczy naraz, obie o tym samym: **stan, ktory deklarujemy, ma byc
stanem, ktory faktycznie obowiazuje**.

## 1. Bramki nie byly odtwarzalne — moj blad z v20.38.1

`parity.py` deklaruje w docstringu, ze baseline i jego dane wejsciowe sa
wersjonowane razem, "wiec bramka jest odtwarzalna na czystym klonie".
Zlamalem to: w v20.38.1 przeliczylem baseline'y wobec **roboczego** configu,
ktory nie byl zatwierdzony.

Zmierzone przed poprawka: zatwierdzony `config.py` mial **531** kluczy i nie
zawieral `DAYTRADING_V2_MAX_SL_PCT`, a baseline zapisal hash z drzewa
roboczego (**536** kluczy). Na swiezym klonie wszystkie cztery bramki byly
by czerwone.

Naprawa: `config.py`, `daytrading_engine_v2.py`, `v2_trade_lifecycle.py`
i zaktualizowane `data/replay/*_30d.json` sa **zatwierdzone razem
z baseline'ami**. Baseline i jego wejscie znow ida w jednym commicie.

## 2. Eksperyment, ktory byl wlaczony wbrew deklaracji

`config.py` mowi wprost: *"Controlled optimization experiments; all disabled
in the production baseline"*. Cztery z pieciu przelacznikow faktycznie tam
stoja na `False`/`0.0`. Piatego **nie bylo w configu wcale**, a
`v2_trade_lifecycle` czytal go tak:

```python
getattr(config, "DAYTRADING_V2_EARLY_CUT_HOURS", 12.0)
```

Brak klucza + domyslka 12.0 = regula `dynamic_time_stop` **aktywna na
produkcji**, wbrew zdaniu w configu. Przelacznik eksperymentu wlaczal sie
sam, przez wartosc domyslna ukryta w kodzie.

### Ile to realnie robilo: nic — i to tez jest wynik

`parity` na 5 symbolach x 30d przed i po wylaczeniu: **58 transakcji,
net -5.8939R, OOS +1.0628R w obu przypadkach**, roznica tylko w hashu
konfiguracji. Regula ani razu nie zadzialala.

Powod jest pouczajacy: warunek wymaga wieku >= 12h, a miekki `time_stop`
stoi na **10h** i wycina pozycje wczesniej. Regula byla wiec martwa przy
obecnym configu — ale **uzbroilaby sie w chwili podniesienia
`TIME_STOP_HOURS` powyzej 12**, czyli dokladnie przy nastepnym strojeniu.

Zadna bramka tego nie widziala: korpus `exit_gate` nie ma przypadku
starszego niz 12h z MFE < 0.3R i ujemnym markiem. Przeliczone baseline'y
potwierdzaja to wprost — po wylaczeniu reguly zmienily sie **po dwie linie
w kazdej bramce** (hash + licznik kluczy), ani jeden wynik przypadku.

### Poprawione

- `DAYTRADING_V2_EARLY_CUT_HOURS = 0.0` dodane do `config.py`, zeby
  "wylaczone" bylo widoczne tam, gdzie sie tego szuka;
- domyslka w `v2_trade_lifecycle` zmieniona `12.0` → `0.0` — przelacznik
  eksperymentu nie moze wlaczac sie przez brak klucza;
- przy okazji dwie domyslki sprzeczne z configiem: `BE_AFTER_TP1` bylo
  `False` (config: `True`), `BE_AFTER_TP2` bylo `True` (config: `False`).
  Dzis niewidoczne, bo klucze istnieja — ale usuniecie ktoregos cicho
  odwrociloby zachowanie. Wyrownane do wartosci z configu.

### Nowy test: `tests/test_v2_experiment_switches.py`

Pilnuje dwoch rzeczy, przy czym **druga jest ta, ktora zawiodla**:

1. kazdy przelacznik istnieje w configu i stoi na wylaczonym;
2. **domyslka w `getattr` tez jest wylaczona** — czytana ze zrodla, bo to
   jedyny sposob sprawdzenia wartosci uzywanej PRZY BRAKU klucza.

Test ma zeby: wzorzec wyciaga domyslke z kodu (`0.0` obecnie), wiec
`12.0` wywrocilby asercje. Dodatkowo `assertGreater(znalezione, 0)` chroni
przed cichym rozjechaniem sie wzorca — inaczej test przechodzilby, nie
sprawdzajac niczego.

W `daytrading_engine_v2.py` galaz `DAYTRADING_V2_15M_SCORING_EXPERIMENT` ma
**oba ramiona identyczne**:

```python
if getattr(config, "DAYTRADING_V2_15M_SCORING_EXPERIMENT", False):
    if not chk: return self._neutral(...)
else:
    if not chk: return self._neutral(...)
```

Flaga nie robi nic, a `DAYTRADING_V2_15M_SCORE_THRESHOLD = 60` nie jest
nigdzie czytany. Zostawione bez zmian — to rusztowanie pod niedokonczony
eksperyment i nie wiem, jaka mial miec docelowa postac. Podobnie zmienna
`timing_mode` jest przypisywana i nigdy nie uzyta.
